# Static site on R2 — feasibility plan (REQUIRED deliverable; build optional)

Goal: a near-zero-cost static experience for `starsky` posters on
Cloudflare R2 (+ Pages/Workers), without blocking the canonical
Gradio app (HF Spaces + Docker).

## Shared render spec (normative for both renderers)

`site/render-spec.json` (to be created on implementation):
colors (`background #0b0f19`, `star #f5efe0`, `line #b98a8a`),
`size = size_max * 10 ** (mag / -2.5)` clamp range, glow alpha/radius
factors, ring width, caption layout (stacked, centered, title-optional),
font stack (`Cormorant Garamond` → `EB Garamond` → serif). The Python
`RenderSettings` defaults must match this file; any visual change updates
both. Prevents Python/JS drift.

## Option A — Fully static (R2 + Pages, zero request-time compute)

- Math in JS: stereographic/fisheye projection + approximate sidereal-time
  alt/az in a small MIT library (`astronomy-engine`); Skyfield precision is
  overkill for posters (arcminute errors invisible at 1600 px).
- Data: trimmed static catalog (Hipparcos mag ≤ ~6.5 → a few hundred KB
  gzipped JSON) + IAU line pairs (same Stellarium source, pre-flattened);
  generated by a `starsky` export command so provenance stays in one place.
- Rendering: Canvas 2D (glow via `shadowBlur`/radial gradients, fisheye via
  the same `r` formula, circle mask via `globalCompositeOperation`,
  caption via Cormorant webfont) replicating the spec tokens.
- Timezone-from-coordinates fully client-side with a compact tz-boundary
  dataset (`tz-lookup`-style lib) — no server call.
- Nominatim CANNOT be called directly from browsers at policy compliance
  (no custom `User-Agent`, no rate-limit control) → one tiny Cloudflare
  Worker as Nominatim proxy/cache (KV-backed, 1 req/s per key) is required;
  everything else stays static in R2. PNG download via `canvas.toBlob()`.
- Cost: R2 free egress + Pages free tier cover hobby scale; Worker free tier
  (100k req/day) suffices with KV caching place queries.

## Option B — Hybrid (static UI, server render)

- Static HTML/JS UI on R2/Pages, but `render_sky_map()` unmodified behind a
  small render API (FastAPI container / HF Spaces / Worker with Pyodide —
  impractical due to size).
- Pros: zero reimplementation/drift risk, full Skyfield precision, PNG/SVG/PDF
  for free. Cons: not "purely static"; keeps a server bill and cold starts.

## Option C (RECOMMENDED) — Canonical Gradio + static preview

Ship the full Gradio app as canonical (HF Spaces + Docker/GHCR/Docker Hub),
and build the R2 static site as a lightweight promotional/preview viewer
(Option A with a reduced feature set: stereographic only, mag ≤ 5.5, no
vector export) linking out to the full app for advanced options.
Rationale: avoids 100% JS feature parity (fisheye-strength, declutter
sliders, SVG/PDF are hard to justify reimplementing), still delivers a
genuinely static near-zero-cost experience, and the shared render-spec JSON
keeps the preview visually consistent.

## Decision

Adopt **C**. Status: `render-spec.json` written; `export-static-data`
shipped; share-link contract (`#s=` payload, see `src/starsky/share/`)
implemented; explorer viewer built at `site/`.
Do not block the main deliverable on this build.

## Appendix — FastAPI render endpoint: rejected for v1 (2026-09-17)

Considered: exposing the Gradio app's pipeline over HTTP (custom FastAPI
routes via `mount_gradio_app`, or a separate service) for the static
client to consume instead of recomputing the sky in JS.

Rejected because:

1. **SDK shape break.** The HF publish artifact is a stock Gradio SDK app
   (`app.py` + `launch()`). Custom mounts deviate from that shape and
   complicate the Space build for zero v1 benefit.
2. **Abuse surface.** One render costs minutes of CPU (Skyfield over
   ~118k stars + matplotlib). An open endpoint with no auth or
   rate-limit primitives in the Gradio SDK is an invitation to burn
   free-tier compute. Proper throttling (per-IP buckets, API keys,
   AbuseIPDB-style filtering) is a whole service of its own.
3. **Sleep/cold starts.** Free-tier Spaces sleep; a viewer dependent on a
   sleeping backend gets multi-minute first loads. Client-side rendering
   is instant and works fully offline after first load.
4. **Redundancy.** The share-link already delivers the use case
   (exact-sky sharing + exploration) with no server, no cost, no logs.

Revisit triggers: client-side precision proven insufficient for print
claims; a funded backend with auth + rate limiting exists; or the app
outgrows the free tier anyway. If revisited, prefer the hybrid shape
(Option B): keep `render_sky_map()` unmodified behind FastAPI, reuse the
share payload as the request body, and put Cloudflare in front for
throttle/caching.

---

## Superseded (2026-09-29)

Option C above is superseded. The refactor (BCRs 0001–0005, ADR-0003) made the
**browser the sole renderer**: the Gradio app and the Python renderer were
removed, the site renders the poster and exports PNG/SVG/PDF, and Python is a
CLI that builds the sky data (`starsky catalog`). The "stereographic only, mag
≤ 5.5, no vector export" preview limits no longer apply — the viewer implements
the full `render-spec.json` (both projections, vector export).
